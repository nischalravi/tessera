## 1. Goal and non-goals

**Goal.** One Git repository per tenant holds every governed access rule: roles and their birthright rules, JIT eligibility, SoD rulesets, agent scopes and detection invariants. A pull request gets a plan (what changes, who gains or loses what, which violations appear or clear); a merge applies the commit atomically after a second person approves; the database records which commit made each object what it is.

**Non-goals.** The bundle never governs Tessera's own RBAC (`internal/auth` permissions, platform users, IdP trust): that stays in the admin-change workflow. No new evaluator for AWS (EP-*), no Terraform input (AC-9), no GitHub App (AC-10). AC-0 writes no code.

## 3. Cedar schema

**Decision D1 (approved): objects are data, rules are policies.** Objects with a fixed shape (Role, JitEligibility, SoD) are YAML documents the loader turns into Cedar entities; predicates over identities or facts (BirthrightRule, AgentScope, Invariant) are Cedar policies. Reason: the data objects already have a YAML or table shape that maps 1:1 (SoD's `tessera.sod/v1` is reused unchanged), and Cedar is used where its validator and analysis add something — conditions. All of them are validated against one schema (`schema/tessera.cedarschema`, generated by `tessera policy schema`, AC-1).

```cedar
namespace Tessera {
  // ---- facts (built from the graph; never authored)
  entity Identity in [Group] = {
    type: String, status: String,            // identities.type / status
    department?: String, title?: String, location?: String,
    attrs: Record,                            // identity attributes (abac.Attrs), open record
    owner?: Identity, sponsor?: Identity,     // NHI owner, agent sponsor
    mfa_strength?: String, created_days: Long,   // strongest enrolled factor (internal/mfa)
  };
  entity Group = { system: String, name: String, privileged: Bool, requestable: Bool };   // an entitlement
  entity Resource = { system: String, environment?: String, tags: Set<String>, privileged: Bool };
  entity Credential = { kind: String, age_days: Long, holder: Identity };
  entity Agent in [Group] = { source: String, kind: String, blueprint?: String };          // view of an ai_agent Identity

  // ---- governed objects (authored)
  entity Role = { key: String, name: String, risk: String, requestable: Bool,
                  owner?: Identity, entitlements: Set<Group> };
  entity JitEligibility = { key: String, principals: Set<Group>, entitlements: Set<Group>,
                            max_hours: Long, approvers: Set<Group>, min_approvals: Long, step_up: Bool };
  entity SodFunction = { key: String, selectors: Set<Record> };
  entity SodRisk = { key: String, priority: String, functions: Set<SodFunction>, ruleset: SodRuleset };
  entity SodRuleset = { key: String, enabled: Bool };

  // ---- actions: one per fact shape
  action birthright  appliesTo { principal: Identity, resource: Role };
  action jit_request appliesTo { principal: Identity, resource: Group,
                                 context: { hours: Long, eligibility: JitEligibility } };
  action reach       appliesTo { principal: [Identity, Agent], resource: Resource,
                                 context: { action: String, action_class: String, system: String,
                                            standing: Bool, via_jit: Bool, via_role?: Role,
                                            fidelity: String } };
  action exist       appliesTo { principal: [Identity, Agent], resource: Resource };   // identity-level facts
  action hold_credential appliesTo { principal: Identity, resource: Credential };
}
```

`reach` facts are rows of `graph.EffectivePermissions` (one per identity, action, resource); `context.fidelity` carries EXACT/APPROXIMATE/UNSUPPORTED so an invariant can refuse to fire on a guess. `action_class` is the AWS catalog access level (list, read, write, permissions_management, tagging) or `admin` for a graph permission marked privileged.

### 3.1 Role (`roles/<key>.yaml`, `schema: tessera.role/v1`)

```yaml
schema: tessera.role/v1
key: payments-analyst          # stable id; name may change
name: Payments analyst
owner: emp-1042                # identity external_id
risk: medium
requestable: true
entitlements: [okta:payments-ro, aws:PaymentsReadOnly]   # system:name, as roles.gname prints it
```

### 3.2 BirthrightRule (`birthright/<role-key>.cedar`)

```cedar
@id("payments-analyst")  @role("payments-analyst")
permit (principal is Tessera::Identity, action == Tessera::Action::"birthright",
        resource == Tessera::Role::"payments-analyst")
when { principal.status == "active" && ["finance"].contains(principal.department)
       && ["human"].contains(principal.type) && principal.attrs.cost_center == "4410" };
```

A **restricted fragment** (as groups §8.2): conjunction of set-membership tests on `department`, `type`, `title` (compiled to `roles.Rule` lists) plus at most one residual condition over `principal.attrs`, compiled to an `abac_policies` row that `Rule.Policy` names. Anything else (disjunction across fields, entity references, `unless`) is a validation error in v1. One birthright policy per role (today's model); see Q3.

### 3.3 JitEligibility (`jit/<key>.yaml`, `schema: tessera.jit/v1`)

```yaml
schema: tessera.jit/v1
key: prod-db-admin
principals: [okta:sre, okta:dba]          # who may ask (group membership)
entitlements: [aws:ProdDBAdmin]
max_hours: 4                              # <= jit.MaxHours (72)
approvers: [okta:dba-leads]
min_approvals: 1
step_up: true
```

The loader also emits one fixed policy (`permit … jit_request … when { principal in context.eligibility.principals && resource in context.eligibility.entitlements && context.hours <= context.eligibility.max_hours }`); authors cannot write `jit_request` policies in v1. Deny by default once a tenant turns eligibility on (AC-5); until then `groups.requestable` keeps working.

### 3.4 SodRule (`sod/<ruleset-key>.yaml`)

Exactly `sod.Bundle` (`tessera.sod/v1`): ruleset, functions with selectors, risks with functions, subjects and remediation. The loader maps it to `SodFunction`/`SodRisk`/`SodRuleset` entities for validation and cross-references. Pairwise conflicts are not expressible as a per-fact Cedar `forbid`, so detection stays in `internal/sod` (D2).

### 3.5 AgentScope (`agents/<key>.cedar`)

```cedar
@id("support-bot")  @agent("entra:7f3c…")        // agent_profiles (source, external_id) or a blueprint app id
permit (principal == Tessera::Agent::"entra:7f3c…", action == Tessera::Action::"reach", resource)
when { ["list","read"].contains(context.action_class) && resource.tags.contains("support")
       && context.system == "aws" };
```

Compiled to a graph invariant: for every `reach` fact of the agent, if **no** scope policy of that agent permits it, a violation `agent_out_of_scope` (key `<scope id>:<identity id>`) is raised with the fact's edges and explanation id. `@blueprint("<app id>")` instead of `@agent` applies the scope to every agent created from an Entra blueprint (`agent_links.blueprint_app_id`). An agent with no scope is reported by the existing `nhi_ownership`/agent posture views, not as out of scope (Q5).

### 3.6 Invariant (`invariants/<id>.cedar`)

Invariants are `forbid` policies over facts, evaluated with an implicit `permit` of everything: a fact for which a `forbid` is satisfied is a violation. Annotations carry today's `Policy` fields (`@id`, `@name`, `@severity`, `@description`, `@message`). Mapping of the 7 YAML types (AC-3 must keep `/api/policies` and `/api/violations` parity fixtures unchanged):

| YAML type | Cedar form |
|---|---|
| `forbidden_access` | `forbid(principal, action == Action::"reach", resource) when { principal.type == "ai_agent" && resource.tags.contains("pii") };` |
| `no_standing_access` | `… reach … when { principal.type == "human" && resource.privileged && resource.environment == "prod" && context.standing && !context.via_jit };` |
| `terminated_with_access` | `… reach … when { principal.status == "terminated" };` |
| `secret_max_age` | `forbid(principal, action == Action::"hold_credential", resource) when { resource.age_days > 90 };` |
| `nhi_ownership` | `forbid(principal, action == Action::"exist", resource) when { ["service","ai_agent"].contains(principal.type) && principal.status == "active" && !(principal has owner && principal.owner.status == "active") };` |
| `mfa_required` | `… exist … when { principal.type == "human" && !(principal has mfa_strength && principal.mfa_strength == "phishing_resistant") };` (the `require` spec key becomes the compared strength; data from `mfa.Load`) |
| `separation_of_duties` | Not ported: `policy.LegacyBundle` already converts it to a SoD risk (§3.4). |

Evidence and edges stay the evaluator's (`Context.evidence`), and `ExplanationID` is filled by `Graph.EdgesExplanation` as today. By default a `reach` fact whose `fidelity` is not `EXACT` never produces a blocking violation (it fails no CI check); it is reported as a low-fidelity finding (Q6).

## 6. Apply semantics

### 6.1 Plan, then apply, in one transaction

1. **Load and validate** (no DB writes, no network): parse every file, check size limits, generate the schema from the tenant's graph, validate entities and policies with cedar-go, run the restricted-fragment checks, resolve every reference. All findings are returned together (`422 invalid_bundle`, diagnostics with path and line).
2. **Plan** (`dryRun = true`): each kind's existing writer runs in dry-run inside one `ReadTenant` transaction and returns its diff (`roles.Plan` steps, `sod.ImportResult`, JIT and scope diffs, invariant violations before and after). The blast-radius hook (§8) adds its summary. The plan is canonical JSON; `plan_sha256` is its digest, and it records `state_digest` (the versions of every object it touches).
3. **Apply**: one `DB.InTenant` transaction re-plans, refuses `409 stale_plan` if `plan_sha256` differs, then runs the same writers with `dryRun = false`, records `policy_ref = {commit, path, bundle_sha256}` on every object and version written, writes `policy_applies`, and appends `policy.bundle.applied` (commit, digests, counts) plus each writer's own domain events to the audit ledger **in the same transaction**. Any error rolls everything back: there is no partially applied commit.
4. **Idempotent**: applying a bundle whose digest equals the last applied one is a no-op that still audits.

Order inside the transaction: SoD functions → rulesets → risks; roles (create, then update, then retire); birthright reconcile; JIT eligibility; agent scopes; invariants last, so invariant evaluation in the plan sees the new roles.

**Size ceiling.** An apply whose role plan exceeds `TESSERA_POLICY_MAX_STEPS` (proposed 20,000 grant steps) is refused with `413 plan_too_large`; the author splits it (Q4). Unlike groups, roles have no async queue, so atomicity wins over size.

### 6.2 Full vs partial

- **partial**: objects in the bundle are created or updated; objects absent from it are left alone. The default for a kind's first import.
- **full**: the bundle is the whole truth for that kind; a repo-managed object absent from the bundle is **retired** (never deleted). Only objects with `managed_by = 'policy_repo'` are retired; UI-made objects are listed as "unmanaged" in the plan and need an explicit `adopt` (imported once with partial) before full mode can retire them.
- **Retire** means: role `status = 'retired'` via `roles.Retire` (its role-sourced grants are removed by the plan; members' other grants stay), SoD `status = 'retired'` via `Prune`, JIT eligibility and agent scopes `status = 'retired'`, invariants disabled. Versions are kept forever (append-only tables).
- **Removals and the deletion guard.** Grant removals in a plan are counted against the deletion guard (`internal/deleteguard`, category `group_members`). Because apply is atomic, an apply over the threshold is refused with `409 deletion_guard` rather than half-held; a second admin may raise the limit for one apply through the existing `deletion_guard.update` change (Q4).

### 6.3 Ownership lock

An object applied from the repo gets `managed_by = 'policy_repo'`; every other writer (UI, API, seed) gets `409 policy_managed`, as groups do. "Export to repository" (later) turns UI objects into files. Drift between repo and database is therefore impossible through Tessera; drift in target systems stays `internal/reconcile`'s job.

### 6.4 Rollback

Reverting the commit and applying it restores the previous definitions (the prior commit's plan). AC-11 adds the post-apply prediction check.

## 7. Two-person apply

- New change type `policy_bundle.apply` in `admin_change_requests` (`0008` CHECK list, applier in `internal/admin/change_policy.go`). Payload: `{commit, repo, bundle_sha256, plan_sha256, mode_by_kind}`; the approver echoes `payload_hash` as today.
- **Requester**: a principal with new permission `policy.apply` (an admin, or the CI API client; after AC-10 the GitHub App's API client). **Approver**: a different human with `admin.change.approve`, step-up required, not the same actor (`SameActor`), and not the PR author when the author maps to a platform user (Q2).
- The approver sees the plan and blast summary that `plan_sha256` names; approval re-plans in the applying transaction and refuses a stale plan, so what was approved is what is applied.
- Requests expire (existing cooling-off and expiry). One pending `policy_bundle.apply` per tenant; a newer commit supersedes (cancels) an older pending one.
- **Recommendation (Q1):** two people for every apply in v1. A later option: a single person may apply a plan that only tightens (no new grant, no new JIT eligibility, no invariant disabled or loosened, no retire), computed from the plan.

## 8. Blast-radius preview hook

```go
// internal/policyrepo (AC-2); implemented by AC-8.
type BlastRadius interface {
    Preview(tx *store.TenantTx, now time.Time, plan *Plan) (*BlastSummary, error)
}
type BlastSummary struct {
    ByIdentityType map[string]Delta  // human, service, ai_agent: gained/lost identities and permissions
    ByResource     []ResourceDelta   // top resources by identities gaining a path
    Violations     policy.Diff       // before/after, from policy.DiffViolations
    RecentlyUsedLost int             // removed permissions used in the window (usage index)
    Approximate    int               // results resting on APPROXIMATE/CONDITIONAL evaluations
}
```

v1 (with AC-4): role plan steps become `simulate.Request.AddEdges`/`RemoveEdgeIDs` and `simulate.Run` gives the identity diff and violations. AC-8 adds AWS operations (`snapshot.Apply` → `query.Diff`) and the principal-to-identity join. The summary is part of the canonical plan, so it is covered by `plan_sha256` and shown to the approver. Endpoints: `POST /api/policy/validate`, `POST /api/policy/diff` (the plan, AC-8's route; `policy.plan`, read-only, audited), `POST /api/policy/apply` (files the change request), `GET /api/policy/applies`.

## 9. Security

- **Untrusted input.** Bundles get the AWS-parser treatment: 256 KiB per file, 4 MiB and 2,000 files per bundle, Cedar nesting depth ≤ 32, ≤ 10,000 entities, annotation values ≤ 1 KiB, fuzzing of the loader and the fragment checks (AC-1). Validation never touches the network.
- **Where the bytes come from.** An apply names a commit SHA. Before AC-10, the bundle is uploaded by CI with its commit and Tessera checks `bundle_sha256`; after AC-10 Tessera fetches the commit itself from the registered repository through `internal/safehttp` with a short-lived App token, so an uploaded body is never trusted for apply. Optional (Q7): require the commit to carry a verified signature from a per-tenant key allowlist.
- **Integrity record.** `bundle_sha256`, `plan_sha256` and commit go in `policy_applies` and in the hash-chained audit ledger; every object version carries `policy_ref`.
- **Tenant scoping.** `tessera.yaml` `tenant` must equal the session's tenant; all reads and writes use the session's `TenantTx`; references resolve only inside the tenant; the per-tenant schema is generated from that tenant's graph. Isolation tests for each new table, and a test that a bundle naming another tenant's slug, keys or groups is refused.
- **Who can do what.** `policy.read` (view sources, applies), `policy.plan` (validate, plan), `policy.apply` (file the change request), `admin.change.approve` + step-up (approve). Seeds and tests apply `Quiet` with no two-person step, never in prod (`internal/config`).
- **Fail closed.** If the bundle store is unreadable, invariants fall back to the embedded YAML set and the UI shows "repository policies unavailable"; JIT with eligibility enabled denies.
- **Scope of Cedar.** The bundle cannot change Tessera permissions, IdP trust, KEK, connectors or write modes.

## 10. Decisions (approved 2026-10-26)

The owner approved the recommendations. Where the draft had none, the safer default is taken.

1. **Two-person for every apply**, including tighten-only plans, through the admin change requests with a plan-hash echo (§7).
2. **Approver vs author:** the approver must differ from the Tessera user who opened the change request (existing four-eyes). Once AC-10 links GitHub logins to platform users, the approver must also differ from the GitHub PR author and merger.
3. **Birthright:** one rule per role in v1 (today's schema); several per role is a later change.
4. **Large or removal-heavy applies are refused** above the step ceiling and above the deletion-guard threshold; no override. Split the change instead.
5. **Unscoped agents:** reported as an `agent_unscoped` finding by default; a tenant can opt in to "no scope = no access".
6. **Invariants on APPROXIMATE facts never block**; they report.
7. **Commit signing is not required in v1**: the GitHub App fetch (AC-10) plus two-person approval is the control. A per-tenant signing-key allowlist can be added later.
8. **Data objects are YAML** (`tessera.sod/v1` reused unchanged).
9. **Add `business_roles.key`** as the stable role key.
